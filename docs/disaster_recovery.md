# DocuGuard AI — Disaster Recovery & Business Continuity Plan

---

## 1. Objectives & Operational Targets

* **Recovery Point Objective (RPO):** Maximum allowable data loss window is **60 minutes** (`RPO_TARGET_MINUTES=60`).
* **Recovery Time Objective (RTO):** Maximum allowable downtime for system restoration is **30 minutes** (`RTO_TARGET_MINUTES=30`).
* **Backup Retention:** Automated retention of backup artifacts is set to **30 days** (`BACKUP_RETENTION_DAYS=30`).

---

## 2. Backup Architecture & Checksum Verification

Every disaster recovery backup generated by `server/services/backupService.js`:
1. Extracts all 17 core relational dataset tables.
2. Serializes data into a versioned JSON snapshot package.
3. Computes an immutable SHA-256 cryptographic checksum.
4. Stores the archive on protected storage (`storage/backups`).
5. Appends a `BACKUP_CREATED` block to the cryptographic `blockchain_audit` ledger.

### Integrity & Corruption Defense
Prior to any restore operation, `verifyBackup(backupId)` recomputes the SHA-256 digest from disk.
* If any byte in the archive has been altered, truncated, or tampered with:
  * Status updates immediately to `CORRUPTED`.
  * An alert event `BACKUP_CORRUPTION_DETECTED` is recorded in the blockchain audit.
  * Restore execution is strictly blocked with `RECOVERY_ERROR`.

---

## 3. Isolated Disaster Recovery Testing

To ensure backups are genuinely recoverable, DocuGuard AI mandates routine restore testing into isolated target environments without touching production tables.

### Execution:
```bash
POST /api/admin/backups/:id/restore
Content-Type: application/json

{
  "dry_run": false,
  "isolation_prefix": "isolated_recovery_"
}
```

The restore runner:
1. Validates the backup hash.
2. Creates isolated tables matching the current schema (`isolated_recovery_documents`, `isolated_recovery_contract_decision_workflows`, etc.).
3. Populates records within a database transaction.
4. Verifies relationship integrity, foreign key references, and record counts.
5. Measures exact elapsed duration in milliseconds and records `RESTORE_COMPLETED` to `blockchain_audit`.

## 4. Operational Metrics Probe

Disaster recovery readiness is monitored continuously via:
```bash
GET /api/admin/backups/metrics
```

Sample Response:
```json
{
  "rpo_target_minutes": 60,
  "rto_target_minutes": 30,
  "last_backup": "2026-09-04T19:15:00.000Z",
  "backup_age_minutes": 15,
  "last_restore_test": "2026-09-04T19:20:00.000Z",
  "last_restore_duration_ms": 1240,
  "rpo_status": "MET",
  "rto_status": "MET",
  "recovery_status": "RECOVERY_READY"
}
```

If the backup age exceeds `RPO_TARGET_MINUTES`, the probe truthfully reports:
```json
{ "recovery_status": "RECOVERY_TARGET_NOT_MET", "rpo_status": "TARGET_EXCEEDED" }
```
